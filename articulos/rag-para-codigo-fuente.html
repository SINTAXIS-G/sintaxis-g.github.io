RAG para código fuente: diez técnicas, con su fuente citada, en un solo store vectorial

RAG genérico para texto y RAG para código fuente no son el mismo problema, aunque compartan la misma infraestructura de base (embeddings + índice vectorial + similitud). El código tiene propiedades que rompen los supuestos de un pipeline de RAG diseñado para prosa: identificadores exactos que importan letra por letra (auth_token_v2 no es semánticamente "parecido" a auth_token_v3 para un embedding denso, aunque para un desarrollador buscando ese símbolo específico la diferencia es todo), estructura jerárquica real (una función vive dentro de una clase, dentro de un archivo, con límites que un chunking por ventana fija ignora), y una relación de importancia que no es solo semántica sino también temporal (código de hace dos años que dice lo mismo que código de ayer no debería rankear igual).

Voy a documentar, técnica por técnica, cómo se resuelve cada uno de estos problemas en un store vectorial que construí sobre ChromaDB — citando explícitamente de dónde viene cada idea que no es propia, porque me parece importante separar qué es una aplicación de una técnica publicada de qué es una decisión de diseño propia.

1. Recuperación jerárquica Parent-Child

El modelo de embeddings usado (all-MiniLM-L6-v2) tiene un límite de 512 tokens. Un archivo de 2000 líneas no cabe. La solución ingenua es truncar — perder el 80% del archivo silenciosamente. La solución correcta, tomada del patrón estándar de recuperación jerárquica en RAG (parent-child retrieval), es indexar chunks pequeños para la búsqueda semántica, pero mantener el documento padre completo disponible para expandir el contexto una vez que un chunk hace match:

def add_document_hierarchical(\...):
\# divide por AST (funciones/clases) con ventana deslizante como fallback
\# cada chunk se embebe e indexa individualmente
\# el documento padre completo va a un KV store separado en disco

El detalle de implementación que me parece correcto: el _ParentStore es un KV store en disco separado, sin embeddings — no contamina el índice HNSW de Chroma con vectores redundantes del documento completo. La separación de responsabilidades es limpia: el índice vectorial solo indexa lo que realmente se va a buscar por similitud; el store de padres solo necesita lookup por ID.

2. Búsqueda híbrida: denso + BM25, fusionados con RRF

Esta es la pieza central del sistema. Similitud coseno sobre embeddings densos es buena para conceptos ("conexión a base de datos" encuentra código de conexión aunque no comparta ni una palabra literal). Es mala para nombres exactos — un embedding no "sabe" que auth_token_v2 es exactamente lo que buscas, solo sabe que es semánticamente parecido a otras cosas relacionadas con autenticación. BM25 (ranking por frecuencia de términos, el estándar de recuperación de información desde los 90) es exactamente lo contrario: encuentra coincidencias léxicas exactas, es ciego al significado.

Correr ambos por separado y quedarse con el mejor no funciona bien porque sus escores no son comparables — la distancia coseno vive en un rango distinto al score BM25, normalizarlos entre sí introduce supuestos arbitrarios. La solución estándar de la literatura de IR es Reciprocal Rank Fusion (RRF), que ignora los scores crudos y fusiona por posición en el ranking:

def _reciprocal_rank_fusion(rankings):
fused = {}
for ranking, k in rankings:
for rank, doc_id in enumerate(ranking, start=1):
fused[doc_id] = fused.get(doc_id, 0.0) + 1.0 / (k + rank)
return fused

RRF es matemáticamente elegante precisamente porque no necesita que las dos listas sean comparables en escala — solo necesita el orden. El tokenizador propio para el índice BM25 además descompone snake_case y camelCase, para que buscar "auth token" también encuentre authToken y auth_token_v2 a nivel de sub-token, no solo coincidencia exacta de string completo.

3. Fusión adaptativa del parámetro k

RRF tiene un hiperparámetro k que controla cuánto peso reciben los primeros puestos de cada ranking (k bajo = más peso a los primeros lugares de esa lista específica). La implementación estándar usa un k global igual para ambos rankers. Aquí se detecta heurísticamente si la query "parece" un identificador de código (pocas palabras, presencia de snake_case/camelCase) y se ajustan los k de forma asimétrica:

if adaptive_fusion and _looks_like_identifier_query(query):
default_dense, default_sparse = 90, 40 \# confiar más en BM25
else:
default_dense, default_sparse = 60, 60

Un k de BM25 más bajo cuando la query parece un identificador le da más peso relativo a sus primeros resultados frente al ranking denso — reconociendo explícitamente que, para ese tipo de query, BM25 es la señal más confiable de las dos. Es una heurística simple (no un clasificador entrenado), pero está bien justificada: el costo de una detección equivocada es solo un peso subóptimo, no un fallo binario.

4. Time-Weighted Search

Dos resultados con similitud semántica idéntica no deberían rankear igual si uno es de ayer y el otro de hace dos años. La ponderación temporal aplica decaimiento exponencial de vida media sobre el score de similitud:

Score_Final = similitud × 0.5^(edad_días / vida_media)

Es la misma familia matemática que el decaimiento radiactivo que vimos en el analizador de código muerto de la conversación anterior — vida media configurable, decaimiento suave en vez de un corte binario tipo "ignorar todo lo de hace más de N días".

5. Deduplicación semántica vía kNN restringido

Antes de insertar un documento nuevo, se consulta el vecino más cercano restringido al mismo filepath (kNN sobre el índice HNSW que Chroma ya mantiene) — no un LSH aproximado aparte, no infraestructura extra. Si la similitud es ≥ 0.995, se actualiza el documento existente en vez de insertar uno nuevo. La decisión de reusar el índice HNSW existente en vez de montar una estructura de deduplicación separada es la correcta aquí: el costo marginal de una consulta kNN adicional, acotada a un filtro de metadata, es bajo, y evita mantener dos estructuras de datos que podrían desincronizarse.

6. Contextual Retrieval — con la fuente citada explícitamente

Esta es la técnica que da título a este artículo. Está tomada directamente de Contextual Retrieval, publicada por Anthropic (anthropic.com/news/contextual-retrieval), y el código lo dice así, sin ambigüedad. La idea del paper: un chunk aislado (return a + b) no dice nada sobre dónde vive ni qué hace — el embedding denso lo indexa "a ciegas" de su contexto. La técnica completa antepone a cada chunk un resumen situacional generado por un LLM antes de embeberlo, y los benchmarks publicados por Anthropic reportan una reducción de ~35-49% en fallos de recuperación quando se combina con BM25 — que es exactamente la arquitectura híbrida que este store ya tiene montada.

Lo que me parece más honesto de esta implementación es lo que no hace: este archivo no llama a ningún LLM directamente. El razonamiento explícito en el código es que una capa de almacenamiento no debería tener una dependencia de red, costo y latencia de un LLM incrustada dentro de su lógica — eso es una violación de responsabilidad de capas. En su lugar, se define una interfaz inyectable:

class ContextEnricher(Protocol):
def enrich(self, chunk: ChunkInfo, full_text: str, filepath: str) -> str: \...

El enriquecedor por defecto es puramente heurístico — antepone archivo, tipo y nombre del chunk ([core/api/auth.py — función autenticar_usuario, línea 42]), que ya resuelve el caso más común de "chunk huérfano" sin costo de latencia ni tokens. Para el enfoque completo del paper, el mismo código deja documentado el punto exacto de extensión:

class LLMContextEnricher:
def enrich(self, chunk, full_text, filepath):
return call_claude(f\"Contexto breve para este fragmento de \"
f\"{filepath} dentro del archivo completo\...\")

Es la forma correcta de referenciar un paper externo en código de producción: implementar la parte que se puede sostener sin dependencias nuevas, ser explícito sobre qué parte de la técnica publicada se está dejando fuera y por qué, y dejar el punto de inyección documentado con el nombre exacto de la clase que alguien tendría que escribir para completar la implementación real.

7. Maximal Marginal Relevance (Carbonell & Goldstein, 1998)

Un ranking combinado de alta calidad puede seguir siendo malo si sus primeros N resultados son casi idénticos entre sí. MMR, publicado en 1998 para resumen extractivo de documentos, resuelve esto maximizando relevancia menos redundancia con lo ya seleccionado:

score = λ · relevancia − (1−λ) · similitud_máxima_con_lo_ya_elegido

La implementación es correcta y con un detalle de eficiencia bien pensado: solo se piden los embeddings de los candidatos a Chroma cuando diversify=True es solicitado explícitamente — es una llamada extra evitable, así que se evita por defecto. Los candidatos sin embedding disponible se tratan con similitud 0 contra todo lo demás (no penalizan ni se benefician de la diversificación), en vez de fallar o sesgar el resultado.

8. Detección y migración de embedding drift

Este es el problema más silencioso de todos los que cubre el sistema, y el que más fácil es no darse cuenta que existe: si el modelo de embeddings cambia con el tiempo (una actualización, un cambio de proveedor), los vectores viejos y nuevos viven en espacios matemáticamente no comparables — comparar similitud coseno entre un vector generado por el modelo A y otro por el modelo B no tiene ningún significado matemático válido, aunque el código no lance ningún error al hacerlo. La degradación es silenciosa: los resultados de búsqueda simplemente empeoran, sin ninguna señal de por qué.

9. GraphRAG-lite: combinar similitud con estructura

La frontera de responsabilidad está explícitamente declarada en el propio código: este store "encuentra qué se parece a esto" (similitud semántica); un grafo de conocimiento aparte "sabe qué está conectado con esto" (aristas de llamada, imports, herencia). Combinar ambas señales es la idea de GraphRAG. La implementación no importa el módulo de grafo de conocimiento directamente — usa el mismo patrón de inyección de dependencia que el enriquecedor de contexto (GraphExpander como Protocol) — precisamente para no crear una dependencia circular entre "quién almacena vectores" y "quién sabe la estructura del código".

10. Corrección honesta sobre un supuesto equivocado

Vale la pena señalar esto porque es coherente con el resto de la serie: en algún punto de la evolución de este archivo se asumió que existía un AsyncPersistentClient en la librería de Chroma para el modo embebido (base de datos local sobre disco, sin servidor). El comentario en el código lo corrige explícitamente: "esto es una precisión sobre el diagnóstico original: AsyncPersistentClient no existe en la librería". La solución real para ese caso es un ThreadPoolExecutor dedicado (no el executor global compartido de asyncio, para no agotar hilos bajo carga) — el mismo patrón que la documentación oficial de Chroma recomienda vía asyncio.to_thread. Para el modo cliente-servidor (con un host de Chroma remoto configurado), sí se usa el AsyncHttpClient real de la librería, porque ahí la operación es genuinamente I/O de red.

Por qué me parece que vale la pena documentarlo así

Cada una de estas diez técnicas resuelve un problema real y específico de hacer RAG sobre código en vez de sobre texto genérico, y ninguna se presenta como más original de lo que es: cuando la idea viene de un paper o de una técnica publicada (Contextual Retrieval, MMR, RRF), el código lo dice, con la fuente. Cuando es una decisión de diseño propia sobre cómo aplicar o adaptar esa idea al caso específico de código fuente (el k adaptativo, la deduplicación restringida por filepath, el drift report), también queda claro que es eso. Me parece que esa distinción, tan simple de mantener, es la que separa una implementación que se puede auditar y confiar de una que solo suena bien.
